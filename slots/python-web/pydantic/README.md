# pydantic

**Slot**: Data validation at API / config / external-data boundaries.

## Why pydantic

The de-facto standard. FastAPI integrates natively. v2 is fast (Rust-backed). Stop hand-writing `if not isinstance(...)`.

## Conventions

- Use pydantic for **boundaries**: HTTP request/response, config files, LLM tool inputs, external API payloads.
- Don't pydantic-ify internal-only data — `@dataclass` or a plain class is enough.
- Use **strict mode** (`model_config = ConfigDict(strict=True)`) for inbound data to catch silent coercion.
- Keep models thin; computed properties belong elsewhere (services, not models).
- Prefer `Annotated[..., Field(...)]` over class-level defaults for documentation.

## Alternatives considered

- **dataclasses** — fine for internal types; no validation, no JSON schema.
- **attrs** — similar story, slightly more features than dataclasses.
- **msgspec** — faster, smaller scope; consider for very high-throughput services.

## Gotchas

- v1 → v2: most code needs `model_validate`, `model_dump`, `ConfigDict`. Don't mix v1 patterns in new code.
- `BaseModel.model_dump()` is the JSON-safe dict; `dict(model)` is not.
- Custom validators: prefer `@field_validator` (per-field) over `@model_validator` (whole-model) when both work.

### What's new since you last touched it

- **`exclude_if` at field level** (2.12) — `Field(exclude_if=lambda v: v is None)` skips a field in `model_dump`/`model_dump_json` based on its value, not a static `exclude={...}` list. Extended to computed fields in 2.13.
- **`extra` parameter on validate functions** (2.12) — `User.model_validate(data, extra="ignore")` overrides the class-level `extra="forbid"` for a single call. Stops you from defining two models that only differ on strictness.
- **`ValidateAs` annotation helper** (2.12) — `Annotated[OutType, ValidateAs(InType)]` cleanly expresses "parse as `InType`, expose as `OutType`" without nested `BeforeValidator` calls.
- **Smarter discriminated unions** (2.13) — when the discriminator selects a variant and that variant fails, validation now errors at that variant instead of silently retrying every other union member. Directly affects your `Pet = Annotated[Union[Cat, Dog], Field(discriminator="kind")]` pattern: errors will be precise.
- **`StringConstraints(ascii_only=True)`** (2.13) — drop-in tightening for fields that should reject non-ASCII (think IDs, slugs, machine names).
- **`__pydantic_on_complete__()` lifecycle hook** (2.12) — runs once when a model's schema finishes building. Useful for late-bound registration without `model_rebuild` dances.
- **Python 3.14 + PEP 695 generics** (2.11 / 2.12) — relevant if you bump above the 3.12 floor.
- **`fractions.Fraction`, UUIDv6/7/8, `SocketPath`** (2.11) — niche but free if you need them.
- **Deprecation: `model_fields` on instances** (2.11) — read it off the class (`User.model_fields`), not the instance.

### Usage example

`exclude_if` cleaning up the `User` model's optional-email serialisation (recommendation #4):

```python
from typing import Annotated
from pydantic import BaseModel, ConfigDict, Field, field_validator


class User(BaseModel):
    model_config = ConfigDict(strict=True, extra="forbid")

    id: int
    name: Annotated[str, Field(min_length=1, max_length=80)]
    email: Annotated[str | None, Field(default=None, exclude_if=lambda v: v is None)]

    @field_validator("email")
    @classmethod
    def lower(cls, v: str | None) -> str | None:
        return v.lower() if v else v


User(id=1, name="Jason").model_dump_json()
# {"id":1,"name":"Jason"}                          # no "email": null

User(id=2, name="Jason", email="J@WISC.EDU").model_dump_json()
# {"id":2,"name":"Jason","email":"j@wisc.edu"}
```

### Use cases

- **Reach for pydantic** at boundaries: HTTP request/response (FastAPI auto-wires it), LLM tool inputs (`fastmcp` derives the JSON schema from your model), config files (delegate to `pydantic-settings`), external API payloads.
- **Reach for `TypeAdapter`** when you need validation but not a named class — `TypeAdapter(list[int]).validate_python(data)` is lighter than declaring a wrapper `BaseModel`.
- **Don't reach for it** for internal-only types: `@dataclass` or a plain class is enough — the README already says this. Also skip pydantic when you're in a hot loop validating millions of small objects; `msgspec` is 5–10× faster and the README already cross-links it.

### Tradeoffs

- **`BaseModel` vs `TypeAdapter`**: BaseModel for entities you'll name, reuse, and document. TypeAdapter for one-shot validation of an arbitrary type (`list[int]`, `tuple[str, ...]`, a `TypedDict`) without inventing a wrapper class.
- **Strict (`ConfigDict(strict=True)`) vs lax**: strict at inbound boundaries (what you do now). Lax internally if you're round-tripping JSON whose number/string coercion you want. Don't mix per-instance.
- **`@field_validator` vs `@model_validator(mode='after')`**: field-level for normalisation and per-field invariants (your `lower` is correct). Model-level when an invariant spans two or more fields (`if foo set, bar required`). Don't reach for `model_validator` first.
- **`exclude_if` (data-dependent) vs `exclude={...}` (static)**: `exclude_if` keeps the field on the model and drops it from the payload conditionally — cleaner than juggling two response models.
